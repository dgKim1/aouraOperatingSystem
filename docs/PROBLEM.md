## 1. 과제 한 줄 요약

8개 업무 중 하나를 골라, **입력 → 확인 → 판단 → 승인 → 상태 변경**까지 실제로 돌아가는 AI 운영 시스템을 만든다.
대시보드·보고서·기획서만으로는 미완성이며, 판단 뒤 승인 요청·작업 생성·상태 변경이 실제로 일어나고 **바뀐 상태가 다음 판단에 쓰여야** 한다.

## 4-1. 운영 시스템 안에서 연결해 보여줄 내용 (추가 전달 사항)

아래 여섯 관점은 **하나의 운영 시스템을 이루는 연결된 관점**이다.
- **온톨로지**는 업무 대상 · 관계 · 상태 · 규칙을 정의한다.
- **데이터 분석과 BI**는 상황 파악과 판단을 돕는다.
- **Agentic workflow와 업무자동화**는 AI · 사람 · 도구의 판단과 후속 처리를 연결한다.

운영 중 AI가 **어떤 정보를 받아 → 어떤 판단 · 처리를 지원하며 → 그 결과가 사람의 결정과 시스템의 실행에 어떻게 쓰이는지** 보여준다.

- 각각을 별도 제품으로 만들 필요는 없다.
- 특정 프레임워크, 그래프 DB, 모델링 문법, Multi-Agent 구조를 강제하지 않는다.
- 선택한 업무와 구현 목적에 맞게 기술 · 구조를 정하고 **그 이유를 설명**한다.

| 관점 | 확인할 질문 | 보여줄 증거 |
|---|---|---|
| **업무 대상 · 관계 · 규칙 (온톨로지)** | 어떤 대상 · 관계 · 상태 · 규칙으로 업무를 이해했는가? | 주문 · 상품 · 원료 · 부서 등의 관계와 규칙, 여러 업무의 조회 · 판단 · 상태를 연결하는 **실제 사용 사례** |
| **데이터의 의미와 연결** | 어떤 정보로 판단하며 무엇이 부족한가? | 출처 · 단위 · 시점 · 연결 기준, 필요한 정보와 공백, 보완 방법을 선택한 이유와 **실제 처리 · 검증 사례** |
| **분석과 대안 비교** | 문제와 대안의 차이를 무엇으로 설명하는가? | 계산 · 비교 · 가정 · 불확실성과 **결론의 연결** |
| **판단을 돕는 화면 (BI)** | 담당자가 무엇을 보고 어떤 결정을 내리는가? | 지표 · 경고 · 근거 · 대안을 보고 **사용자가 결정할 수 있는 화면** |
| **AI · 사람 · 도구의 운영 역할** | 운영 중 AI가 맡는 역할은 무엇이며 사람 · 도구와 어떻게 연결되는가? | AI가 받는 정보 · 만드는 결과, 사람의 승인 · 예외 판단, 도구 실행과 계획 · 상태 갱신으로 이어지는 **실제 흐름** |
| **판단 이후의 처리** | 판단 이후 어떤 반복 작업이 처리되는가? | 결정 · 회신에 따라 생성 · 갱신된 요청 · 계획 · 작업 · 문서와 처리 이력, **결과가 다음 판단에 반영되는 사례** |

W02 에서 각 관점을 어떻게 보여줄지는 [W02_TASK.md](W02_TASK.md) 8절.

## 5. 함께 지켜야 할 원칙

1. **주장과 사실 구분** — 부서가 작성한 전망·회의 의견·분석 결과는 사실이 아니라 **작성자의 주장**으로 구분해 검토한다.
   (예: `00_common/mkt_meeting_notes_ms.md`, `01_corevia/sales/sales_meeting_notes_cv.md`, `01_corevia/financials/sales_memo_cv.md`, `04_celtonic_labs/docs/celtonic_management_interview.md` 등)
2. **제약을 임의로 없애지 않기** — 원본의 생산능력·계약·승인 등 제약을 가정으로 지우면 안 된다.
3. **유리한 회신만 만들지 않기** — 모의 회신을 유리한 것만 만들어 검증을 대신할 수 없다. (거절·부족 케이스 필요)
4. **추가 확장도 심사 대상** — 대표 업무 외 확장도 평가하지만, **설계 단계의 확장이 필수 구현을 대신하지는 않는다.**
