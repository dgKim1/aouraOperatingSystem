> 출처: 대회 참가 페이지 「업무 고르기 / 자료 살펴보기 / 완료 조건」 (2026-11-10 기준 옮겨 적음).
> 원문 상세는 `01_참가자_배포용/A01.html`(상세 문제지)을 기준으로 한다. 이 문서와 원문이 다르면 원문이 우선이다.

## 1. 과제 한 줄 요약

8개 업무 중 하나를 골라, **입력 → 확인 → 판단 → 승인 → 상태 변경**까지 실제로 돌아가는 AI 운영 시스템을 만든다.
대시보드·보고서·기획서만으로는 미완성이며, 판단 뒤 승인 요청·작업 생성·상태 변경이 실제로 일어나고 **바뀐 상태가 다음 판단에 쓰여야** 한다.

## 4. 완료 조건 (다섯 가지 모두 충족해야 제출 가능)

| # | 조건 | 내용 | 확인 |
|---|---|---|---|
| 1 | **실제로 돌아가는 시스템** | 입력을 넣으면 확인 → 판단 → 승인 → 상태 변경까지 이어진다. 외부 승인·발주는 실제로 보내지 않고 **모의 회신**(가짜 회신)으로 대신해도 된다. | ☐ |
| 2 | **세 가지 상황 시연** | ① 정상 ② 조건 변경 ③ 정보 부족 또는 승인 거절. ②와 ③은 이어서 보여줘도 된다. | ☐ |
| 3 | **나만의 확장 1개 이상** | 내 경험·관심을 살려 데이터, 조건, 예외를 하나 더 다루고, 그것이 **실제 판단이나 처리를 바꿔야** 한다. 예: 화장품 품질 업무 경험 → "출하처 확인 상태" 추가, 미확인 배치는 보류. | ☐ |
| 4 | **다른 부서 영향 1개 이상** | 내 업무의 결정이 다른 부서의 목표·제약에 영향을 주고, 그 때문에 **대안이나 계획이 달라져야** 한다. 예: 회수 때문에 영업팀 대형 고객 납품이 밀려 재공급 우선순위 조정. 확장과 같은 사례로 함께 보여줘도 된다. | ☐ |
| 5 | **원본과 가정 구분** | 제공 데이터로 확인한 것과, 내가 가정하거나 새로 만든 데이터를 구분해 표시한다. **원본 파일은 고치지 않는다.** | ☐ |

## 5. 함께 지켜야 할 원칙

1. **주장과 사실 구분** — 부서가 작성한 전망·회의 의견·분석 결과는 사실이 아니라 **작성자의 주장**으로 구분해 검토한다.
   (예: `00_common/mkt_meeting_notes_ms.md`, `01_corevia/sales/sales_meeting_notes_cv.md`, `01_corevia/financials/sales_memo_cv.md`, `04_celtonic_labs/docs/celtonic_management_interview.md` 등)
2. **제약을 임의로 없애지 않기** — 원본의 생산능력·계약·승인 등 제약을 가정으로 지우면 안 된다.
3. **유리한 회신만 만들지 않기** — 모의 회신을 유리한 것만 만들어 검증을 대신할 수 없다. (거절·부족 케이스 필요)
4. **추가 확장도 심사 대상** — 대표 업무 외 확장도 평가하지만, **설계 단계의 확장이 필수 구현을 대신하지는 않는다.**

## 7. 제출 전 자기점검

- [ ] 업무 번호(W0x)를 정하고 제출 화면에 표시했다
- [ ] 입력 → 확인 → 판단 → 승인 → 상태 변경이 끝까지 동작한다
- [ ] 바뀐 상태가 다음 판단에 반영된다
- [ ] 정상 / 조건 변경 / 정보 부족·승인 거절 3가지를 시연할 수 있다
- [ ] 나만의 확장 1개 이상이 판단·처리를 실제로 바꾼다
- [ ] 다른 부서 영향 1개 이상으로 대안·계획이 달라진다
- [ ] 화면·결과에 원본(확인) / 가정(새로 만든 것)이 구분 표시된다
- [ ] 원본 파일을 수정하지 않았다
- [ ] 회의록·전망·분석은 "주장"으로 표시했다
- [ ] 원본 제약(생산능력·계약·승인)을 임의로 없애지 않았다
- [ ] 모의 회신에 거절·부족 케이스가 포함된다
- [ ] A04 설명서 양식 문항에 답할 수 있다
